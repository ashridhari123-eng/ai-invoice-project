Architecture

A stack a solo fresher can actually ship

Frontend

  • React + TypeScript (Vite)
  • Component library: shadcn/ui or Ant Design (tables, forms, drawers come free)
  • Charts: Recharts
  • State/server-cache: TanStack Query

Backend

  • Node.js (NestJS) or Python (FastAPI) — pick the language you're strongest in
  • REST API + JSON
  • Background jobs: BullMQ / Celery (email polling, matching, syncs)
  • Auth: JWT + role claims

Data & infra

  • PostgreSQL — one database, relational, transactional
  • Object storage for PDFs (S3-compatible)
  • Redis for queues/cache
  • Docker Compose for local dev

Advice: resist microservices. One well-structured monolith with clear modules is the right architecture for one developer. Split later only if forced to.

Data model

Core entities and how they link

organizations ─┬─ users ── roles / approvals_delegations
               ├─ budgets (dept + category + period, amount)
               ├─ vendors ── vendor_bank_accounts (maker-checker!)
               ├─ items (catalog, HSN/SAC, default tax)
               │
purchase_requisitions ── pr_lines ──────────────┐  (line-level links!)
        │ approvals[]                           │
rfqs ── rfq_lines ── rfq_vendors ── quotes ── quote_lines
        │ award decision                        │
purchase_orders ── po_lines ◄───────────────────┘
        │ approvals[]
goods_receipts ── grn_lines (received/accepted/rejected qty, po_line_id)
invoices ── invoice_lines (po_line_id nullable) ── match_results
payments ── payment_lines (invoice_id, tds_amount) ── advances (adjustments)
audit_log (append-only: entity, action, actor, before/after, timestamp)

Two rules that save you later

  • Link at line level, not just header level — matching, partial receipts, and budget consumption all happen per line.
  • Store money as NUMERIC(14,2) (never float) and keep currency on every document.

Every document table gets

  • doc_number from a per-entity, per-year series (PO/2026/00042)
  • status, created_by, created_at, updated_at
  • org_id for multi-entity isolation
State machines

Every document is a state machine

Never store status as a free string that any code can set. Define allowed transitions and enforce them in one place.

PR

DRAFT→SUBMITTED→APPROVED→CONVERTED
SUBMITTED→RETURNED / REJECTED

PO

DRAFT→PENDING_APPROVAL→APPROVED→SENT→PARTIALLY_RECEIVED→CLOSED

Invoice

CAPTURED→EXTRACTED→MATCHED→APPROVED→SCHEDULED→PAID
MATCHED→EXCEPTION→RESOLVED / REJECTED

Implement one generic transition(doc, from, to, actor, reason) function that validates the move, writes the audit log, and fires notifications. Every module reuses it.

The engine room

Approval workflow engine

Design: rules + instances

approval_rules
  doc_type      "PR" | "PO" | "INVOICE"
  conditions    {amount_min, amount_max,
                 department?, category?}
  steps         [{order, approver_role
                  | approver_user, sla_hours}]

approval_instances
  doc_id, rule_id, current_step
  actions[] {step, user, decision,
             comment, timestamp}

Behaviour to implement

  • On submit: evaluate rules top-down, pick first matching, create instance
  • Approve → advance step; final step → doc becomes APPROVED
  • Reject → back to requester with mandatory comment
  • SLA breach → reminder, then escalate to approver's manager
  • Delegation: out-of-office table redirects tasks
  • SoD check: requester ≠ approver, enforced in code

This one engine powers the "Pending approvals" KPI, the Inbox, and the touchless rate (auto-approve rule for amounts under a threshold). Build it well, build it once.

Every query is scoped by org_id (the entity switcher in the top bar). Permissions = role → set of module:action strings checked in middleware. Keep it boring and explicit.

API design

REST endpoints — a representative slice

POST   /api/prs                     # create draft PR
POST   /api/prs/:id/submit          # state transition, starts approval
POST   /api/approvals/:id/decision  # {decision: "approve"|"reject", comment}
POST   /api/rfqs                    # from approved PR lines
POST   /api/rfqs/:id/quotes         # record vendor quote (or AI-extracted)
POST   /api/rfqs/:id/award          # {vendor_id, reason} → drafts PO
POST   /api/pos/:id/send            # email PDF to vendor, status → SENT
POST   /api/grns                    # against PO lines
POST   /api/invoices/ingest         # from email watcher (Module 3)
POST   /api/invoices/:id/match      # run 2/3-way match, returns exceptions
POST   /api/payment-runs            # proposal from due invoices
GET    /api/dashboard?from=&to=     # all KPI cards in one call

Conventions

  • State changes are verbs as sub-resources (/submit, /award) — not PATCHing a status field
  • Idempotency keys on ingest & payment endpoints
  • Cursor pagination on all lists

Validation lives server-side

  • Budget check on PR submit
  • SoD check on approval
  • Qty billed ≤ qty accepted on match
  • UI checks are convenience only
The homepage

Computing each dashboard card

CardQuery sketch (period-filtered)
Touchless rateinvoices where human_touches = 0 ÷ all processed invoices. Increment a counter on every manual edit/decision.
Pending approvalscount(approval_instances where status='PENDING') — clicking opens the queue
Avg cycle timemedian(paid_at − received_at) on paid invoices. Note the scope toggle in the UI: AP (receipt→pay) vs full P2P (requisition→pay)
Monthly throughputsum(invoice.total) processed this month
MSME at riskunpaid invoices of MSME vendors where today − received_at ≥ 35 days (warning window before 45)
Budget utilizationsum(committed + spent) ÷ sum(allocated)
PR cycle timemedian(decided_at − submitted_at)
Sourcing savings(pr_estimate − awarded_value) ÷ pr_estimate over awarded RFQs

Compute these in SQL with a single date-range parameter; cache for 60s. The "cycle time trend" chart is the same median grouped by week for 12 weeks.

Cross-cutting

Notifications, files, audit

Inbox & notifications

  • One notifications table: user, type, doc link, read flag
  • Events: task assigned, approved/rejected, exception raised, SLA breach, MSME warning
  • In-app bell + daily email digest is enough for v1

Documents & files

  • Store PDFs (invoices, quotes, PO prints) in object storage; DB keeps metadata + SHA-256 hash
  • Hash catches duplicate invoice files instantly
  • Generate PO/remittance PDFs from HTML templates

Audit log

  • Append-only, no update/delete grants
  • Row: actor, entity, action, before → after JSON, IP, timestamp
  • Written inside the same DB transaction as the change
  • This is a feature (sidebar: "Audit Log"), not just plumbing
Quality

Testing a workflow system

Where tests pay off most

  • State machine: every illegal transition rejected
  • Approval rules: boundary amounts (₹25,000 vs ₹25,001), delegation, SoD
  • Matching engine: table-driven tests — a CSV of PO/GRN/invoice combos with expected outcomes
  • Budget math: committed/accrued/spent across the whole lifecycle

Practices

  • Seed script that creates a demo org: 5 users, 10 vendors, 20 items, budgets — so every feature is demoable in one command
  • One end-to-end "golden path" test: PR → pay
  • Feature branches + PR review (ask a senior to review weekly)
