The AI Modules

Two AI-powered features turn a workflow tool into a "command center": (A) comparing RFQ responses and recommending an award, and (B) extracting invoices from email for automated 2/3-way matching. Both follow the same philosophy: AI proposes, humans approve, rules verify.

Prerequisites: Modules 1 & 2. You'll need an Anthropic API key for the exercises.
Philosophy first

Where AI belongs in P2P — and where it doesn't

AI IS GREAT AT

  • Reading unstructured documents: invoice PDFs, quote emails, scanned images → structured JSON
  • Normalising messy vendor language ("free delivery above 50k", "90 days credit")
  • Summarising trade-offs between quotes and drafting a recommendation with reasons
  • Flagging anomalies: unusual prices, near-duplicate invoices, odd vendor behaviour

AI MUST NOT

  • Approve spend or release payments — a human always makes the final award/pay decision
  • Be the only validation — deterministic rules (totals add up, GSTIN format, qty ≤ received) always run after extraction
  • Operate without confidence scores and a human-review fallback

Pattern to remember: LLM for understanding, code for arithmetic and rules, humans for judgement. Never let the LLM do the maths that your matching engine can do exactly.

AI Module A · RFQ

A. Quote comparison — the problem

Three vendors reply to your RFQ, each in their own format: one fills your form, one sends a PDF, one writes prices in an email body. The buyer needs a fair, side-by-side comparison and a defensible decision.

Vendor AVendor BVendor C
Unit price (100 units)₹480₹455₹470
FreightIncluded₹2,500 extraIncluded
Payment termsNet 45100% advanceNet 30
Delivery7 days21 days10 days
Warranty1 year6 months1 year

B has the lowest unit price — but add freight, the cash-flow cost of 100% advance, and 3-week delivery, and B may be the worst offer. Naive lowest-price comparison is the bug your AI module exists to fix.

AI Module A

Step 1 — Normalise every quote to landed cost

Deterministic (code, not AI)

landed_unit_cost =
  unit_price
  + (freight + packing + other) / qty
  + non_creditable_taxes / qty

# payment-terms adjustment (cost of capital, e.g. 12%/yr)
cash_cost = amount × rate × (advance_days / 365)

GST that you can claim as input credit is usually excluded from comparison — compare pre-tax landed cost unless credit isn't available.

Where AI helps

  • Extracting these fields from each vendor's PDF/email into one schema (same technique as invoice extraction — slide 8)
  • Interpreting fuzzy terms: "freight free above ₹50,000", "2/10 net 30", "ex-works Pune"
  • Flagging what a vendor didn't quote (missing warranty, no validity date) so the buyer can chase it
AI Module A

Step 2 — Score with weighted criteria

Weighted scoring model

CriterionWeightScoring
Landed cost50%lowest = 100; others = lowest ÷ price × 100
Delivery time20%fastest = 100, linear scale
Payment terms15%more credit days = higher
Vendor rating15%from past OTIF % & quality history

Weights are configurable per category — urgent spares weight delivery higher; commodities weight price higher.

Step 3 — LLM writes the recommendation

Feed the normalised table + scores to the LLM and ask for a structured recommendation:

{
 "recommended_vendor": "Vendor C",
 "reasoning": "Lowest total landed cost after
   freight; Net 30 terms; 10-day delivery
   meets the need-by date. Vendor B's advance
   payment adds ₹4.1k cash cost and delivery
   misses the deadline.",
 "risks": ["C's quote valid only 15 days"],
 "negotiation_tips": ["Ask A to match ₹470"]
}

The buyer sees the comparison grid + AI recommendation, can override with a reason, and clicks Award. The decision + reasoning is stored — that's your audit trail and the "Sourcing savings" number.

AI Module B · INV

B. Invoice capture from email — the pipeline

1 · WATCHDedicated mailbox e.g. invoices@co.com — poll IMAP or use Gmail/Graph API push
→
2 · INGESTPull attachments (PDF/images), hash file, store in object storage, create invoice in CAPTURED state
→
3 · EXTRACTSend document to LLM with a strict JSON schema → structured invoice + confidence
→
4 · VALIDATEDeterministic checks: totals, GSTIN, duplicates, vendor lookup
→
5 · MATCH2/3-way match vs PO & GRN; pass → auto-approve route; fail → exception queue

Ingestion details

  • Idempotency: message_id + file hash unique key — the same email processed twice must not create two invoices
  • Non-invoice attachments (signatures, T&Cs) — let the classifier step drop them
  • Keep the raw email + file forever; link them to the invoice record

AI Module B

Extraction: schema-first prompting

# Python — Anthropic API, PDF in, JSON out
import anthropic, base64, json
client = anthropic.Anthropic()  # key from env ANTHROPIC_API_KEY

pdf_b64 = base64.b64encode(open("invoice.pdf","rb").read()).decode()

msg = client.messages.create(
  model="claude-sonnet-4-6", max_tokens=2000,
  messages=[{"role":"user","content":[
    {"type":"document","source":{"type":"base64",
     "media_type":"application/pdf","data":pdf_b64}},
    {"type":"text","text":"""Extract this vendor invoice. Respond with ONLY
JSON matching this schema, no prose:
{"vendor_name":str, "vendor_gstin":str|null, "invoice_number":str,
 "invoice_date":"YYYY-MM-DD", "po_number":str|null, "currency":str,
 "lines":[{"description":str,"hsn_sac":str|null,"qty":num,
           "unit_price":num,"tax_rate_pct":num,"line_total":num}],
 "subtotal":num, "cgst":num, "sgst":num, "igst":num,
 "grand_total":num, "confidence":0-1,
 "notes":"anything ambiguous or unreadable"}
Use null for missing fields. Never guess a PO number."""}]}])

data = json.loads(msg.content[0].text)

Schema-first = the prompt is mostly a JSON contract. "Never guess" instructions + a notes field for ambiguity dramatically reduce hallucinated values.

AI Module B

Validate before you trust

Deterministic checks (code)

  • Arithmetic: Σ line totals = subtotal; subtotal + taxes = grand total (re-compute, don't trust)
  • GSTIN: 15-char format check; matches a vendor in your master
  • Duplicate: same vendor + invoice number, or same file hash, or same (vendor, amount, date) → block
  • Date sanity: not in the future, not 2 years old
  • PO exists and belongs to this vendor

Confidence routing

ConditionRoute
confidence ≥ 0.9 and all checks passStraight to matching (touchless path)
0.7 – 0.9, or any null critical fieldHuman verifies in Inbox side-by-side view
< 0.7 or arithmetic failsManual entry; keep the sample for prompt improvement

Log every human correction — that's your accuracy dataset.

AI Module B

The matching engine (deterministic core)

# 3-way match, per invoice line — pseudocode
def match_invoice(inv):
    po = find_po(inv.po_number, inv.vendor_id)          # header link
    exceptions = []
    for line in inv.lines:
        po_line = best_po_line(line, po)                 # see below
        if not po_line: exceptions.add(line, "NO_PO_LINE"); continue
        accepted = sum(g.accepted_qty for g in grns(po_line)) - already_billed(po_line)
        if line.qty > accepted + qty_tol(po_line):       exceptions.add(line,"QTY_OVER_RECEIPT")
        if abs(line.unit_price - po_line.price) > price_tol(po_line):
                                                          exceptions.add(line,"PRICE_MISMATCH")
        if line.tax_rate != po_line.tax_rate:             exceptions.add(line,"TAX_MISMATCH")
    return "MATCHED" if not exceptions else ("EXCEPTION", exceptions)

Line pairing is the hard part

Vendors rename items ("HP Laptop 15s" vs "Laptop HP-15s-fq5111TU"). Pair by: PO line ref if quoted → item code → fuzzy description similarity + same qty/price. An LLM call is a good tie-breaker for ambiguous pairs — but the qty/price comparison stays in code.

Exception queue UX

Each exception shows the three documents side by side with the conflicting numbers highlighted, and actions: accept variance (with reason, within authority), request credit note, return to vendor, edit pairing. Every action → audit log.

Making it trustworthy

Measure, guard, improve

Evaluation set

Collect 30–50 real invoices (anonymise if needed) with hand-verified "golden" JSON. After any prompt/model change, run the set and score field-level accuracy. Target: >95% on invoice number, date, totals; >90% on lines.

Guardrails

  • API keys server-side only, never in frontend
  • Cap spend: max tokens, retries with backoff, dead-letter queue for failures
  • PII care: invoices contain bank details — restrict access by role
  • Model output is data, never executed as instructions

Improvement loop

  • Weekly: review human corrections, cluster failure types
  • Fix with prompt tweaks or a validation rule — retest on the golden set
  • Watch the touchless rate on your dashboard climb — that's the KPI this whole module moves
